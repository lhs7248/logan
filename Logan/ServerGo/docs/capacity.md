# 压测执行与容量边界

工具与示例见 [负载工具说明](../tests/load/README.md)。`cmd/loadtest` 不依赖 k6，提供 health、Native read/upload/mixed、QPS/并发/渐增流量和有界队列，输出成功率、错误类别、超时、丢弃和 p50/p95/p99。合成上传数据来自既有 Java 协议向量；业务查询可能触发解析写入，必须使用专用数据库和 OSS 前缀并明确允许写入。

## 执行顺序

1. 建立隔离 MySQL/OSS，记录版本、CPU/内存/连接数、数据规模和日志大小分布，配置相同协议密钥及预算。
2. 从真实 SDK 合成数据预置任务和详情，记录 Native TaskID/DetailID。生成器只生成请求文件，不会替你插入数据库，随机无效 ID 不能用于测业务成功率。
3. 先以 health 验证工具和 HTTP；再以低 QPS 执行业务，确认返回内容、解析状态和对象一致。
4. 分别测首次解析、解析后读取、上传及混合流量，逐档提高 QPS/并发。记录客户端丢弃，不能把未发出的请求从负载证据中隐藏。
5. 在相同资源和数据副本上分别运行 Java/Go，预热与测量窗口一致，保存原始 JSON 与服务端 CPU/RSS/GC、DB 等待/慢查询、OSS 延迟和任务积压。
6. 注入依赖故障后观察恢复，另做长稳测试。只有错误/丢弃、p99、资源和积压均满足冻结的 SLO，才确定额定容量；只看 RPS 比值不足以得出结论。

```sh
go build -tags stdjson -o /tmp/logan-loadtest ./cmd/loadtest
/tmp/logan-loadtest --base-url http://127.0.0.1:18080 --allow-test-target --mode health --qps 200 --concurrency 8 --queue 16 --duration 10s --output /tmp/health.json
```

该命令只做 HTTP 健康冒烟，不能作为业务容量。业务命令、合成 fixture 和写入开关见工具说明；压完后清理本次专用资源。当前工具覆盖 Native 三类工作负载，尚未提供 Web 协议上传、全部查询组合、跨服务资源采样或自动化 24 小时稳态报告。不要把脚本可运行等同于这些场景已验收。

## 当前测量范围

本轮执行临时 Go 服务的健康接口冒烟，并用业务关闭返回 501 做失败对照；原始结果和最终参数记入 [阶段进度](progress.md)。没有启用真实 OSS 的业务压测，也没有 Java/Go 同条件容量对比。当前不能承诺业务 QPS、生产 p99、部署规格或性能提升比例。后续应优先补齐测试 OSS 和业务种子数据，再执行上述完整流程。
