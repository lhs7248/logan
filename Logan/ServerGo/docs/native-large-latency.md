# 32 MiB Native 解析与 brief 等待（阶段 23）

本阶段只修改并测试 Go，不运行 Java，不使用生产数据、不切流。原 Java 作为只读兼容参考保留。

## 已确认的问题与修复

1. 多个本地 worker 能从重叠的 Pending 扫描中拿到同一 ID。数据库 CAS、租约和 fence 保证了单次发布，但无效抢占仍可能等待发布事务持有的行锁并占用连接。新增每实例的活跃任务预留；数量最多为 Workers，成功、失败、取消后均释放。同一实例跳过重复尝试，跨实例仍必须经过原来的数据库 CAS、租约、fence、revision 和 digest 校验。没有改变发布事务的原子性。
2. 原逐字节分行每字节调用 context.Err，并逐字节通过 bufio.ReadByte。改为有界片段读取及批量 CR/LF 搜索，保留 CR、LF、CRLF、行/记录预算、取消、Java 投影与历史 gzip 处理。32 MiB 本机解析微基准约 180.04 → 84.09 ms；这只是解析微基准，不是端到端提升，也不是容器 QPS。
3. brief 原来每 10 ms 查询持久状态，改为每 100 ms 查询，仍能看到其他实例的发布。不根据本地通知宣称跨实例完成，也不返回不完整的成功结果。
4. Go 原默认等待 5s，而合法后台处理预算为 30s。Java 首次 brief 会同步分析后再返回，没有相同的 5s 限制。未显式设置 LOGAN_NATIVE_QUERY_WAIT 时，现默认跟随 LOGAN_NATIVE_QUERY_TIMEOUT（默认 30s）。显式 5s 保留，调用方取消及外层 HTTP 超时仍有效。此项是等待行为变化，不是性能优化；不能用它把解析变慢说成变快。

上一阶段的 10/22 次失败没有在本阶段同资源的 220 秒基线中重现。不能据此证明历史慢请求的具体分段原因，也不能把全部历史失败归因于上述某一项代码开销。

## 分段计时与端到端口径

每次实际取得任务所有权后输出一条无正文的 `native processing stages` JSON 事件，包含任务数值 ID、有限错误分类、总执行时间和以下耗时。没有取得所有权的 CAS 空操作不会输出这条事件。

| 阶段 | 口径 |
| --- | --- |
| queue | 首次尝试从数据库创建任务到读取已持有任务快照，全部使用数据库时钟，包含抢占和首次快照开销；重试不把之前执行与退避时间当成排队时间 |
| download | 获取 OSS 对象、读取压缩数据并写入私有临时文件；此处不是移动端上传时的 AES 解密 |
| decompress | gzip 解压到有界明文暂存文件，包括历史连续 member/分帧兼容处理 |
| parse_stage | 明文记录转换及 NDJSON 暂存编码/写入，失败也保留已消耗时间 |
| stage_decode | 发布期间从暂存流解码记录，逐批累计 |
| db_insert | 批量 INSERT 调用耗时，逐批累计 |
| publication | 整个发布事务，包括取得连接、锁、旧数据清理、解码、INSERT、续租、状态更新及 COMMIT |

publication **包含** stage_decode 和 db_insert，不能相加。queue 包含所有权快照阶段，与总执行时间有部分重叠，也不能直接相加。单条事件不含日志内容、OSS 路径、密钥或 SQL。

`cmd/soaktest` 的 `upload_to_all_details` 分 Native/Web 单独记录单调时钟样本：从发起上传前开始，到所有预期明细 ID 和正文逐批成功读取并按 oracle 核对完毕结束。包含期间的接口检查、轮询、网络及客户端核验，是“全部日志已读到并核验”的保守端到端上界，不能解读为数据库刚发布的最早时刻。

最终样本输出 P95/P99（nearest-rank）。未达到完整明细里程碑的流程单列 Censored，存在此类失败或仍有活跃上传时，不输出无条件 P95/P99；成功条件分位数另列。未启动/丢弃的到达由原到达账目报告。里程碑后的其他接口失败仍使整个流程失败，不抹去已验证的读取耗时。中间快照仅列条件分位数，避免慢请求尚未返回时误报正常。

Native 依旧在首次 brief 时触发后台解析；没有改成上传后自动解析。端到端统计保留这个触发顺序。

## 隔离环境与可比性

专属 ARM64 VM：3 CPU、4 GiB、8 GiB 磁盘。Go 1 CPU/1 GiB、GOMAXPROCS=1、GOMEMLIMIT=768MiB；MySQL 8.4.11 1 CPU/2 GiB、buffer pool 256 MiB、max_connections=16；Go pool 8/4。redo 128 MiB、binlog 64 MiB/60s，仅适用于可丢弃测试库；sync_binlog=1、innodb_flush_log_at_trx_commit=1 保持。负载端 0.5 CPU/1 GiB，本地 OSS 字节替身 0.25 CPU/512 MiB。

每档 220 秒、0.2 个流程/秒、并发 2、队列 4、突发 2，44 个流程，其中 Native/Web 各 22。协议正确的合成大日志为 1/1、8/4、32/8 MiB（Native/Web）；真实原 SDK 产物仅为小样本、RSA 2048，不代表真机生成的 32 MiB 产物。没有外部 OSS 签名认证、TLS、多机或 24 小时长稳认证。

基线镜像含分段计时，尚无性能修复；先比较固定 5s 的修复版，再测试新默认等待预算。单档各 22 个 Native 样本，P99 实际接近最大样本，不能视为高置信度容量结论。宿主当时负载及文件缓存会影响结果，没有重复多轮统计实验。

### 受控超时复现与恢复

在两个串行、独立的测试库中，给相同原 SDK 小样本对象的第一次 GET 注入 6s 延迟：

- 旧默认 5s：brief 约 5.005s 返回 HTTP500（错误体为空）；后台继续完成，排空后两条明细内容和哈希正确，重复读取 ID 稳定。
- 修复默认 30s：brief 约 6.104s 返回 HTTP200/code200 和全部结果；重复读取 ID 稳定。
- 两端均只有一个处理尝试，done、owner 为空、lease=0、fence/revision/attempt=1、digest 长度64、无遗留错误。此处旧版的 HTTP500 是预期的注入故障，不计作零错误压测。

这直接证明默认等待预算不匹配会让合法后台任务在 brief 提前失败，并验证修复行为；不能反推上一阶段所有慢请求的具体物理瓶颈。
