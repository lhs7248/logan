# Go 候选发布、切换与回滚

本文件提供待审批、待演练的操作方案，不执行生产启动、迁移或切流。原 Java 服务、镜像、配置、数据库和 nginx 文件均保留。当前 `/readyz` 固定返回 503，真实 OSS、目标平台容器及容量尚未验收，**当前状态不得切流**。`/livez=200`、容器 healthy、Prometheus up=1 都不能解除这个阻断。

部署候选见 [部署说明](../deploy/README.md)，监控见 [监控说明](../deploy/monitoring/README.md)，测试边界见 [集成验证](integration.md)。

## 1. 发布材料与门槛

发布负责人为每次演练建立记录：变更单、代码版本、Go/Java 不可变镜像 digest、目标平台/资源、网关现行配置校验和、时间窗口、数据域、备份位置、恢复负责人及明确的判停阈值。候选 tag 仅供构建，正式发布以扫描通过的 digest 固定；本次尚未生成或扫描镜像。

进入生产窗口前以下项目必须全部通过，否则留在隔离环境：

- 在目标 Linux/Docker 构建和启动镜像，验证 UID10001、只读根、私钥可读、临时目录可写且0700、512MiB配额、内存/CPU/PID/FD限制及OOM/磁盘满/重启处理。非 root 配置渲染不是运行证明。
- 用真实隔离 OSS、目标 MySQL版本和SDK数据跑完整接口、签名下载、Native/Web解析、重复/覆盖行为、多实例、依赖故障和容器 SIGTERM/SIGKILL。对比原Java，无未解释差异；501/空fixture/禁用功能不得算通过。
- 同资源容量、长稳与恢复达到事前冻结SLO。告警模板的5%/2.5秒/100任务只是初值，不能拿来替代SLO。不能到切换当天再定义成功标准。
- 监控可抓取、告警可触发并恢复。当前 receiver 是 blackhole；实际通知渠道、接收人和投递测试需单独明确授权与演练，本轮没有发送通知。
- 在生产副本上验证原Java可读取Go新写的四表/OSS数据，完成往返回滚演练和写入对账。当前MySQL进程测试不能替代此项。
- 完成与现有状态匹配的真实 readiness 实现及发布验收。当前没有 readiness 旁路开关，禁止把负载均衡健康条件改成 `/livez` 来绕过503。

## 2. 备份和迁移

先核对原Java镜像/配置/密钥与MySQL/OSS归属，确保恢复材料可以实际恢复。备份包含原四表及新增处理/上传锁/维护/对象登记/命名空间表，使用一致性方案；保存OSS对象清单、前缀/生命周期和可恢复版本，记录RPO/RTO。数据库备份不等于OSS对象备份，已物理删除对象不能靠数据库回滚恢复。

迁移001/002只由独立的、已批准步骤执行并记录校验和，不在容器ENTRYPOINT、Compose depends_on或健康检查中执行，不使用AutoMigrate。确认InnoDB、索引和事务语义。新建内部表保留到回滚后，不执行down/drop；原Java忽略新表，不代表已经验证所有数据语义。

回滚窗口内Go维护保持false，避免不可逆删除。原Java `LogCleanTask` 的每日02:00 cron是硬编码，当前没有可直接使用的关闭环境变量：仅阻断入口不能停掉Java清理。进入同一生产数据域的Go运行期前必须排空并停止原Java进程，或先交付并验证单独的Java任务停用方案；不得虚构开关。

## 3. 隔离候选与网关准备

候选使用独立 `logan-go-candidate` 项目，宿主回环端口18080，不接入原frontend/Java网络，不创建生产数据库，也不改变原Compose。准备仓库外0600私密env文件与只读私钥目录，全部业务开关先关闭；按部署说明逐项在专用DB/OSS中开启。Go模板worker=1和1GiB/512MiB只是保守起点，不是额定容量。

保持当前前端鉴权、CORS与外部路径不变：外部 `/logan/...` 对应后端 `/logan-web/logan/...`。两个待审阅片段在 `deploy/gateway/`，后缀 `.example`，没有被任何Compose/nginx include。它们必须经实际网关配置检查与隔离端到端请求验证后才可采用。

Go片段使用 `logan-go:8080`，原Java片段使用 `backend:8080`，宿主/容器网关需先明确其网络位置。容器内的127.0.0.1不是宿主；独立候选DNS也不会自动出现在原frontend网络。只有在审批后的窗口才能调整网关网络/上游；不要把Go加入旧项目并重命名为backend来隐式替换Java。

候选片段增加32MiB正文预算、HTTP/1.1和流式转发，需与原有有效网关限制/Go配置一起核对，不能不经验证覆盖现网限制。保留原路径尾斜线、查询参数、Host和转发头。禁止在一个upstream中随机混合Java/Go，禁止跨版本自动失败重试：查询也可能触发解析写入。

## 4. 短维护窗口切换状态机

首期采用整数据域维护切换，不采用按请求随机灰度。下面是方案，当前不执行。

1. **JAVA_ACTIVE**：Java独占数据域，Go候选只连隔离副本。确认新部署材料及回滚门槛全部通过，提前准备维护入口与当前Java网关配置快照。
2. **ENTRY_CLOSED**：在统一入口阻断该数据域全部业务请求，包括上传、查询、下载入口及后台/直连客户端；维护响应和重试行为需提前告知。不能只封POST，GET首次查询会写解析结果。内部不再发兼容探针或读请求到生产数据。
3. **JAVA_DRAINED**：等待已有HTTP及解析结束，检查Java日志、数据库活动事务/连接与清理任务，再优雅停止Java；确认没有遗留Java进程/cron/其他写入口。保留镜像、原Compose和数据库，不执行down -v。
4. **GO_CLOSED**：确认迁移/备份和配置，再在入口仍关闭时启动Go连接该数据域，维护保持false。检查实例、私钥/OSS/DB、真实业务开关与readiness。不得在Java仍可解析/清理时启动Go任务worker；没有只读探针模式可代替此限制。
5. **GO_CANARY**：readiness与所有门槛已通过后，只在受控入口发少量合成事务并核对四表/明细/对象。若使用真实生产写入，需单独批准并记录其ID和清理/保留方案。未写入前的失败可直接退回Java；写入后的失败进入下述兼容性回滚分支。
6. **GO_ACTIVE**：统一入口整域切到唯一Go上游，分阶段恢复业务，观察错误码、p95/p99、积压、DB等待、OSS与资源。24小时观察只是计划门槛，尚未执行。Java继续保持停止；到回滚窗口结束且保留策略确认后，再单独评审开启Go维护。

入口恢复之前必须确认单一写入者；数据库lease/fence只协调Go，原Java不遵守它们。不能依靠“等30秒租约到期”来证明Java已停止，也不能只看HTTP在途数判断后台解析/清理结束。

## 5. 回滚步骤

故障触发值由事前SLO和数据一致性标准决定。出现误删、部分发布、协议不兼容或持续写入异常时，先关闭统一入口，保全日志和数据证据；不把请求自动回退到仍运行的Java。

1. 关闭该数据域所有业务入口/直连路径。停止新的Go容器重建/自动扩容，禁止继续发诊断业务查询。
2. 在入口关闭状态，对当前项目优雅停止Go（部署说明的 `stop -t 90 logan-go`，正式镜像使用相同的release overlay），等待HTTP/worker/维护退出；确认全部Go副本、重试/清理进程和数据库事务均已停止。超时强杀需记录未完成任务，再核对持久化状态，不立即启动第二套写入者。
3. **尚未产生Go业务写入**：核对备份和Java配置后，可恢复原Java；新增内部表仍保留，先验证数据状态再恢复入口。
4. **已经产生Go写入**：先按已演练的兼容性方案核对新增任务、状态、详情ID、Web覆盖和OSS可读性，再决定是否直接恢复Java。不能未经验证把原snapshot覆盖回去：这会丢失Go期间的成功上传。若必须恢复备份，需另行批准明确数据损失/补偿、数据库与OSS一致的恢复点及恢复演练，不能自动执行。
5. 只有确认Go不会再写/清理后才启动Java，检查其解析和硬编码清理任务的影响；先在入口关闭状态验收，再恢复**原**Java上游。保存本次网关配置、镜像digest、状态/对象差异和恢复时间。
6. 不删除新增内部表、tombstone或待回收记录，不重置OSS命名空间绑定。不把lease行置零作为跨Java/Go切换方法。再次上线Go前对账Java期间的新上传、修改和清理；不能信任旧done状态或未更新的对象登记，需已验证的对账方案。

## 6. 演练记录与当前验证范围

每次演练记录每个状态的进入/退出时间、唯一写入者、被停止进程、已接受/失败请求、任务/明细/对象核对、监控告警结果、回滚耗时和数据损失。以完整接口及对象可用性为成功依据，不能只记“容器启动”。

第七阶段完成离线Compose与监控验证；第八阶段补充基础容器验收；第九阶段通过隔离Linux arm64的活跃HTTP/任务排空、Native/Web SIGKILL租约恢复、真实Java/Go数据层及选定读接口往返，入口见[故障与兼容演练](recovery-rehearsal.md)。原Java源码未改，测试WAR使用隔离配置与JRE17工具链，不等于原JRE8镜像复验。具体证据以[进度记录](progress.md)为准。真实OSS、外部通知、全部接口/上传下载兼容回滚、nginx reload及生产恢复仍未验收；没有生产数据库/对象写入、原Java停机或生产入口变更。

## 7. 本次可重复验证入口

Docker 镜像、挂载权限、资源限额、退出和隔离往返拓扑演练入口见[容器验收说明](container-validation.md)。它使用 Java 模拟器，不代替本手册的真实数据兼容回滚门槛。

```sh
python3 script/check-deployment.py --compose /path/to/docker-compose --promtool /path/to/promtool --amtool /path/to/amtool
python3 -m unittest discover -s tests/tools -v
```

从ServerGo执行。离线检查只使用临时合成env，验证候选和release叠加模型、固定digest形态、端口/权限/资源/挂载及告警配置/fixtures；它不读取生产私密env，不构建、拉取、启动容器，不迁移、不切流。工具缺失返回blocked/退出2，检查失败退出1；退出0只证明离线检查通过。正式环境的真实digest有效性、镜像签名和漏洞扫描还需发布系统验证。

同一项发布应始终使用相同Compose文件顺序、project名和私密配置路径；不要将候选Compose与旧Java Compose做文件合并。第八阶段仅在可丢弃VM内拉取测试镜像、启动随机命名的隔离候选Compose并回收；没有执行生产启动、原Java停机或网关reload。
