# 需求复核与日志入口纠偏

日期：2026-10-19。范围：本地产品原型；没有接真实接口，没有修改原 Logan 业务实现。

## 结论

**部分符合，不能宣称整体验收通过。** 此前 24 项状态测试通过，仅覆盖有限示例流程。原型后续迭代过度偏向 AI，将日志任务入口收进了工单，将解析缩成回捞的一步，偏离了原需求。原 Logan 工作副本 `git status --short` 为空，Native/Web 页面和 Go 解析实现保留。

本轮已经补回一级导航：日志任务、日志解析、日志阅读。日志任务跨工单可查；解析可单独查看来源、文件、状态、错误和索引是否发布，成功后可进入正文或下载样例。AI、工单、源码作为关联能力。修改只位于 prototypes/logan-investigation。

## 本轮复现的问题（未修复）

每个模型边界用合成对象重复运行两次，原始结果见 [model-probes.json](evidence/requirements-audit/model-probes.json)。这是独立的验收诊断，不是已通过的既有 24 项测试。

1. **历史证据回写可能被同 ID 新内容覆盖。** 回答快照保存 old source；移出上下文再补入同 ID 的 new source，回写使用 new source。回答生成依据与工单证据可能不一致。模型级重复复现，尚未补做浏览器全流程复现。
2. **无日志的非登录问题仍生成登录假设。** 对“支付重复扣款，应先补充哪些信息？”提问，空证据下依然出现“登录失败路径未恢复加载状态”等固定假设。模拟能力可以有限，但场景不匹配时应明确提示不足，不能将登录样例当通用调查。模型级重复复现。
3. **不同设备与构建可被当作对应源码。** 合成输入分别来自 device-A/build100 和 device-B/build200，当前规则仍写“对应失败分支的版本匹配源码”。尚未校验任务、设备、版本、构建的一致性。模型级重复复现；真实仓库未接入。

此外，多轮目前保留历史轮次关系与验证快照，但模拟规则没有通用的代词消解、澄清或跨轮语义理解；不能把可输入任意文字等同于具备任意自然语言排查能力。

## 信息架构再次纠偏

用户指出此前七个并列导航混合了业务对象、处理步骤与辅助工具，该批评成立。恢复日志能力不应通过堆叠一级菜单完成。

现有原型改为三个业务对象：

- 日志中心：已接收日志的查找、状态、解析详情、阅读、搜索、上下文和下载。
- 采集任务：回捞请求、推送回执、设备确认、上传、处理结果和重试；没有收到文件的请求不再列作已有日志。
- 问题工单：问题背景、关联资料、调查对话、源码证据、假设验证和处理结果。

解析、阅读是选定日志的详情操作；推送是采集阶段；源码与 AI 属于上下文工具。移除了以数据“存在”冒充完成状态的勾选步骤条，改成关联资料数量。原路由仍可访问，既有本地数据未删除。

已在浏览器验证：TASK-208 解析与阅读保持同一日志上下文；进入排查明确切换到 ISS-1042 工单；采集列表保留全部 5 个请求及超时状态，日志中心只展示 4 份已接收来源。检查时未捕获 JavaScript 错误，1440px 文档无横向溢出。

独立按设备发起、不关联工单的采集尚未实现，创建入口当前明确选择关联工单，不会隐式沿用上一个打开的工单。其他未完成能力和前述三个 AI 边界问题仍未因导航调整而解决。
