本轮按 ux-heuristics 做启发式评估，当前流程约 **4/10**（主观走查评分，不是用户研究）。达到完整设计目标需要同时满足：目标身份可信、字段来源明确、范围含义准确、错误可恢复、结果能支持下一步。修改后还应进行首次使用者任务测试，不能仅凭作者评分认定 10/10。

## 1. 已核验的具体问题

| 严重度 | 观察与依据 | 对用户的影响 |
| --- | --- | --- |
| 3 重大 | 新建表单没有应用、环境、平台、版本和构建的确认区；设备只是自由文本 | 用户不知道日志属于哪个现场，错误目标不容易在提交前发现 |
| 3 重大 | 请求模型从工单继承 version/build，platform 缺省为 Native；表单不传这些字段 | 更换设备仍携带旧构建；Web 目标也可能被标记为 Native，影响源码关联 |
| 3 重大 | 能力下拉框位于目标选择之前，默认支持精确时段及类型；切换工单只更新设备和时间 | 用户承担系统能力判断；切换目标后旧能力配置仍在 |
| 3 重大 | “实际采集范围”由用户时间和能力模式计算，尚无返回日志证明；可读文件数量被放在“覆盖”标题下 | 容易把请求计划或文件处理成功理解为现场覆盖完整 |
| 3 重大 | 全局新建必须选择工单，并默认沿用上次活动工单 | 临时取日志被迫先建立工单；可能误关联旧问题或已解决问题 |
| 2 次要 | 长表单把目标、范围、能力演练、预算和有效期放在一起；提交区在折叠窗口下方 | 发起动作的主次不清，容易漏看关键输入 |
| 2 次要 | 列表主要展示编号、设备和工单；详情先显示范围，再显示请求身份 | 同设备的多个任务难区分，用户难判断应看哪次及下一步 |

## 2. 先明确采集任务是什么

采集任务表示“为了取得某个现场的历史日志，向明确目标发出一次请求，并追踪返回材料”。工单是调查上下文，可以提供线索；它不能替代设备身份、设备能力或日志内的构建信息。

需要分开的对象：

- **用户意图**：查谁、什么故障、何时发生、希望取得什么材料。
- **发送目标**：项目/应用/环境 + 安装实例或 Web 会话；普通用户标识只用来查找目标，不能直接等同推送地址。
- **执行计划**：能力允许的时间粒度、混合文件或分类、预计范围、等待期限和资源限制。
- **实际结果**：设备响应、返回文件、文件身份、解析结果、观察到的事件时间和缺口。

原型仍可使用合成对象，但对象间关联必须明确，未知值不能用固定样例补成“已确认”。

## 3. 推荐的发起流程（待实现）

### 从工单补采

进入补采即显示工单现象、目标和故障时间，注明“来自工单，待核对”。系统按应用、环境及设备/会话解析唯一目标；如果有多个安装或会话，要求选择。故障构建与设备当前构建分开展示。默认继承工单的调查范围，用户只调整本次需要的材料和时间。

已解决工单发起新采集时明确用途：为重新调查补证，或者创建独立采集后再决定关联；不能无提示沿用关闭状态的旧上下文。

### 从采集中心新建

不应依赖上次活动工单。建议三个连续步骤，保留返回、取消与草稿：

1. **确认采集目标**：当前项目/应用/环境默认继承工作空间并可见；搜索设备、安装或 Web 会话；显示最近联系时间、身份来源与能力更新时间。关联工单可选。仅有设备字符串但无法解析目标时保存草稿或改用导入，不假装已经可以发送。
2. **选择故障范围**：填写故障发生时间和前后范围，允许自定义；明确时区。能力按目标自动带出，展示预计按日采集或精确采集。只提供真实支持的类型；按日混合文件说明后续可筛选。上限、等待期限和提醒放入可展开的高级设置。
3. **核对并发起**：用一张摘要卡确认目标、时间、预计材料、额外范围及关联工单。仅在扩大范围等必要情况下额外确认。主按钮“发起日志回捞”；未知能力或不可送达说明原因并提供替代动作。

提交后落在该请求的详情，显示“等待设备响应”和明确的下一步。工单补采保留“返回调查”；独立采集提供“关联已有工单 / 从日志建立问题”。

这个方案改变了现有 issueId 必填和 requests 嵌入工单的原型模型。实现时须同步修订接口与对象约束，以独立采集对象加可选工单关联承载；不能只在表单增加“无工单”选项。旧请求仍保留原 ID 和关联。

## 4. 元数据归属与信任规则

| 信息 | 谁提供、何时确认 | 页面行为 |
| --- | --- | --- |
| 项目、应用、环境 | 工作空间或明确选择 | 始终可见；换应用后清除不兼容目标选择 |
| 平台、安装/会话标识 | 目标记录；手动录入仅为未核验线索 | 不固定默认 Native，不从标题猜平台 |
| 故障现象、故障时间 | 用户或工单 | 可修改本次请求，不反写旧工单现场 |
| 故障版本/构建 | 工单提供预期；日志/构建映射确认实际 | 分为预期、最近已知、日志实际；不互相覆盖 |
| SDK 版本、能力、推送通道 | 目标能力记录，带来源及时间 | 只读展示；过旧/未知明确提示，演练开关移出业务表单 |
| 请求时间与预计范围 | 用户意图 + 能力计算 | 分别叫“希望获取的时段”“预计采集范围” |
| 返回内容时间 | 文件声明及解析结果 | 标明来源，先显示未知；没有内容不能显示完整覆盖 |
| 请求编号、发起人、创建时间、阶段 | 系统生成 | 详情可追踪，不让用户手填 |

设备升级后仍可能返回旧构建日志；一个文件也可能包含多个构建。源码关联应在资产/事件层使用可核验构建，并将混合或缺失身份标为未知。当前设备构建不能直接覆盖故障日志构建。

## 5. 任务详情应回答的问题

详情先显示“为哪个问题、向哪个目标、回捞哪个时段”，再显示进度和结果。建议保持现有三个入口及能力，调整详情顺序：

1. 任务身份：应用/环境/平台、目标、请求编号、发起时间、关联问题。
2. 当前结果和主操作：等待响应、处理中、可读、部分失败、无日志、失败或取消；每种状态给下一步。
3. 材料概览：返回文件数、成功解析数、观察到的事件时间段、是否命中目标时段、已知缺口。
4. 文件明细与日志入口：按资产/解析批次打开；部分成功可以先阅读，再只补缺失部分。
5. 推送和处理时间线：作为可展开的诊断信息，保留渠道受理、送达未知、SDK 回应等事实。

“采集完成”仅表示本次处理结束。日志首末时间包含故障时刻也不证明中间无缺失；完整覆盖需要设备/文件覆盖清单等依据。没有依据时显示“已有相关事件，连续覆盖尚未确认”。

## 6. 下一轮必须验证的任务

- 首次用户不建工单也能发起一条身份明确的独立采集，并从结果进入阅读及建立问题。
- 从工单补采时，不重填已有线索；能看到并纠正目标身份与工单线索冲突。
- 切换 Native/Web 或设备后，能力重新读取，旧目标能力及未核验构建不串用。
- 最近已知构建与日志实际构建不同，源码关联以对应日志的身份为准。
- 按日采集的计划范围、文件返回范围和事件观察范围清楚区分。
- 等待响应、未知回执、部分成功、空日志、取消和迟到结果都有明确下一步。
- 所有已有导入、Web 样例、解析与重试、源码、AI、多轮补证、修复验证及回写功能继续存在；旧 ID、证据和记录不变。

本轮只完成分析、浏览器走查和隔离模型复现，没有修改交互代码或真实接口，也没有重新执行 90 项回归测试。该纠偏方案尚未作为实现通过结论。
