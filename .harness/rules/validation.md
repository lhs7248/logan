# 验证与证据

任务先记录目标、范围和可观察的验收标准；小任务留在会话，跨阶段契约和决策放到工程文档。复用已有测试，增加测试应覆盖实际行为或故障边界。

| 变更 | 最低验证选择 | 不能据此声称 |
| --- | --- | --- |
| Harness 文档/配置/脚本 | check、self-test；执行受影响 profile | 业务验收通过 |
| Go 普通逻辑 | 相关测试，交付时 quick | 真实依赖可用 |
| 并发、协议、任务或构建 | full，加相关兼容样本 | 真实 SDK、崩溃恢复通过 |
| Java 基线 | java，人工核对差异，再运行 Go 测试 | 完整 Java 部署一致 |
| 前端或 SDK | 对应组件现有测试/构建，必要时运行行为验证 | 其他组件已验证 |
| 产品页面、交互或原型落地 | 前端行为验证，以及按 [设计基线规则](design-fidelity.md) 逐页对照和流程验收 | 接口或功能测试通过即代表设计交付完成 |
| 数据库、OSS、多实例 | 隔离真实依赖下的集成场景 | 替身测试可以替代集成 |

缺工具、缺凭据、网络不可达或未实现的验证要明确报告为受阻/未执行，不忽略失败继续宣称完成。报告范围、命令、退出码、证据位置和剩余缺口。避免无关全量构建。

执行机制：run.py 为所选命令记录结果；范围和证据充分性由评审兜底。失败处理：定位失败，修复任务范围内问题；环境受阻如实记录。没有 CI 强制机制，也没有自动证明需求覆盖的能力。
